# Report Export Design

## Goal

CodeHarbor should generate a shareable evaluation report from data it already collects, without requiring the user to copy terminal output, Docker logs, or project metadata by hand.

## Scope

This batch adds local Markdown report export for one environment. It includes report generation, report listing, and simple opening actions from the UI. It does not add PDF export, HTML preview, grading/scoring, cloud sharing, report editing, or custom report templates.

## Backend Behavior

Reports are generated by a Tauri command and written under `~/.codeharbor/environments/<id>/reports/` as append-only Markdown files named with a timestamp, for example `report-20260809-153000.md`.

The report generator reads existing backend-owned sources:

- environment metadata from `environment.json`
- project inspection data from the existing project inspection logic
- evaluation history from the existing history reader
- Docker compose config and recent Docker logs from the existing Docker inspection commands

The generator must be best-effort. If project inspection or Docker inspection fails, it still writes the report and includes an explicit error section for the failed source. Missing optional data should not abort export unless the environment ID or environment metadata is invalid.

The backend exposes these commands:

- `generate_evaluation_report(environment_id: String) -> Result<ReportFile, String>`
- `list_evaluation_reports(environment_id: String) -> Result<Vec<ReportFile>, String>`
- `open_report_file(environment_id: String, report_name: String) -> Result<(), String>`
- `open_report_folder(environment_id: String) -> Result<(), String>`

`ReportFile` includes the file name, absolute path, creation timestamp, and file size in bytes. Report names accepted by `open_report_file` must be plain file names inside the reports directory. Absolute paths, path separators, and `..` are rejected.

## Report Content

Each report contains these sections:

- `Summary`: environment name, environment ID, generation time, host path, and a note that this is not an automated grade.
- `Project`: Makefile presence, detected Make targets, language counts, executable candidates, and artifacts.
- `Evaluation History`: recent runs sorted newest-first with command kind, label, success state, duration, and start time.
- `Latest Outputs`: truncated stdout and stderr/error text from recent runs.
- `Valgrind`: Valgrind entries extracted from history, including target labels and truncated output.
- `Docker`: compose config and recent logs, or explicit error text if unavailable.
- `Manual Review Notes`: fixed reminders that generated reports support human evaluation but do not replace manual review.

Large text blocks are truncated to keep reports readable. The first version uses fixed limits: latest command output blocks up to 4,000 characters each and Docker logs/config up to 8,000 characters each. Truncation is marked in the Markdown.

## UI Behavior

The current Evaluation page gains a focused `Reports` panel, separate from Build/Test/Valgrind actions. It includes:

- `Generate report`
- recent report list with file name, size, and timestamp
- `Open latest` when at least one report exists
- `Open folder`

After generation, the UI refreshes the report list and writes a concise success message to the existing output panel. If generation fails, the existing output panel displays the backend error.

The frontend does not assemble report content. It only calls backend commands and renders metadata.

## Data Model

Reports are durable files owned by the environment directory. Deleting an environment deletes its reports together with the generated environment assets. Project files under `~/.codeharbor/projects/<id>/` remain untouched, matching the existing deletion behavior.

Report files are append-only. Regenerating a report creates a new timestamped file instead of overwriting the previous one.

## Error Handling

Invalid environment IDs return an error and do not create files. Missing environment metadata returns an error and does not create files.

Secondary source failures are embedded in the report:

- Docker unavailable or stopped environment: include Docker error section.
- Project folder missing: include Project error section.
- Empty history: include an explicit empty-state line.

Opening a report must validate the report file name and fail if the file does not exist inside the reports directory.

## Testing

Add Rust unit tests for:

- generating Markdown into the reports directory from a minimal environment fixture
- listing reports newest-first
- rejecting unsafe report names for open operations
- including required sections in generated Markdown
- truncating long output with a clear marker

Existing verification commands must continue to pass: `cargo test`, `cargo check`, and `npm run build`.
